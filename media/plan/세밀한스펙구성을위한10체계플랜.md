# Plan: SDD 스펙 구조 정립 — 10섹션 체계 도입

## Context

현재 `SPEC_SYSTEM_PROMPT`(SpecGenerator.ts)와 `/spec guide`(ChatViewProvider.ts)는
frontmatter 필드 + 수락 기준 4케이스 + `## API / ## 컴포넌트 구조 / ## 예외 처리` 5개 섹션만 정의되어 있다.
Props 타입 명세, 내부 상태(State), 조건부 렌더링 규칙(Render Logic), 이벤트 핸들러 명세가 없어서
복잡한 페이지 스펙을 작성해도 AI가 코드 생성 시 내부 로직을 추정(hallucination)할 수밖에 없다.

목표: 10개 섹션 + 복잡도 등급(L1/L2/L3) 기반 스펙 구조를 코드베이스 전반에 반영하여
AI 생성 스펙과 개발자 수동 스펙 모두 세밀하게 작성될 수 있도록 한다.

## Step 1 — knowledge/spec-guide/spec-structure.md 신규 생성

**목적**: RAG가 주입하는 레퍼런스 문서 + 개발자가 직접 참조하는 가이드.

**frontmatter**:
```yaml
---
title: SDD 스펙 작성 구조
category: spec-guide
keywords: [spec, 스펙, 스펙구조, spec-guide, spec-structure, 섹션, 복잡도, L1, L2, L3,
           component-tree, props, state, render-logic, events, form, edge-cases]

---
```

**문서 본문 구성**:

### 복잡도 등급 (complexity frontmatter 필드)
```
L1 (단순): 정적 화면, 단순 조회       → 필수: 수락 기준 + 개요 + API + 예외 처리
L2 (표준): 목록·상세·폼 화면          → L1 + 상태 + 이벤트
L3 (복잡): 다중 API·다단계 폼·복합 모달 → L2 + 컴포넌트 트리 + Props + 렌더 조건 + 폼(해당시)
```

### 10개 섹션 정의 (각 섹션별 작성 규칙 + 짧은 예시 포함)

| # | 섹션명 | 등급 | 핵심 규칙 |
|---|---|---|---|
| 0 | `## 수락 기준` | 전체 필수 | 4케이스 체크리스트 (기존 유지) |
| 1 | `## 개요` | 전체 필수 | 1~2줄. 목적 + 핵심 흐름 |
| 2 | `## 컴포넌트 트리` | L3 | 들여쓰기 계층, 서브컴포넌트 경로 명시 |
| 3 | `## Props` | L2+ | TypeScript interface 형태. 라우터 params는 useParams()로 별도 명시 |
| 4 | `## 상태` | L2+ | Server State(useApi)와 Local State(useState) 구분, 타입 명시 |
| 5 | `## 렌더 조건` | L3 | "조건 → 결과" 형태. isLoading/error/empty 3단계 분기 항상 포함 |
| 6 | `## 이벤트` | L2+ | "사용자 액션 → 동작 순서". onSuccess/onError 시점까지 명세 |
| 7 | `## API` | 전체 필수 | useApi 시그니처 그대로. enabled 조건, invalidateQueries 대상 포함 |
| 8 | `## 폼` | L2+, 폼화면만 | zod 스키마 + 필드별 검증 + submit onSuccess/onError |
| 9 | `## 예외 처리` | 전체 필수 | 로딩/빈값/에러 3가지 기본. UI 처리 방법(Skeleton/EmptyState/Toast 등)까지 |
| 10 | `## 미결정 사항` | 선택 | - [ ] 형태 열거 |

## Step 3 — SpecGenerator.ts: SPEC_SYSTEM_PROMPT 수정

새 프롬프트 구조:
```
당신은 react-app-scaffold 기반 프로젝트의 SDD 스펙 작성자입니다.

코딩 규칙:
- API: useApi(@axiom/hooks) 훅만 사용
- UI: @axiom/components/ui (shadcn 기반)
- 라우팅: createHashRouter + loadable()
- 열린 파일의 타입·구조와 일관성 유지

frontmatter 필수 필드:
  title, category, domain, screen, owner, status(초기값 draft), complexity, tags
  금융 화면 추가 필수: compliance-tags, reviewer

복잡도 등급 (complexity 필드에 반드시 명시):
  L1 (단순): 정적/단순 조회 → 수락 기준 + 개요 + API + 예외 처리
  L2 (표준): 목록·상세·폼  → L1 + 상태 + 이벤트
  L3 (복잡): 다중API·복합 모달·다단계 폼 → L2 + 컴포넌트 트리 + Props + 렌더 조건 + 폼

섹션 작성 규칙:
## 수락 기준 (전체 필수, frontmatter 바로 다음)
  - [ ] 체크리스트 4케이스: 정상/로딩/빈값/에러

## 개요 (전체 필수)
  1~2줄. "무엇을 하는 화면" + "핵심 데이터 흐름"

## 컴포넌트 트리 (L3)
  들여쓰기 계층. 서브컴포넌트는 파일 경로 명시.

## Props (L2+)
  TypeScript interface 형태.
  라우터 params는 useParams<{id: string}>()로 받으므로 별도 명시.

## 상태 (L2+)
  ### Server State (useApi): 변수명, 타입, endpoint
  ### Local State (useState): 변수명, 타입, 초기값

## 렌더 조건 (L3)
  "조건 → UI" 형태. isLoading/error/empty 3단계 반드시 포함.

## 이벤트 (L2+)
  핸들러명(파라미터): 1.동작 2.동작 순서로. API 호출 시점, onSuccess/onError 포함.

## API (전체 필수)
  useApi<TData, TVariables>('endpoint', { method }) 시그니처 그대로.
  enabled 조건, invalidateQueries 대상 명시.

## 폼 (L2+, 폼 화면만)
  zod 스키마 코드블록 + 필드별 검증 규칙 표 + submit onSuccess/onError 동작.

## 예외 처리 (전체 필수)
  표 형태: 케이스 | 조건 | UI 처리 (Skeleton/EmptyState/Toast 등)

## 미결정 사항 (선택)
  - [ ] 형태. 승인 전 반드시 해소.

출력 형식: YAML frontmatter가 포함된 마크다운 스펙 문서만 반환.
다른 설명 없이 스펙 문서 단독으로 출력하세요.
```
