먼저 링크의 내용을 확인해볼게요.내용을 잘 파악했습니다. 핵심 문제를 정리하면:

**기존 1단계 플랜**: 초기 corpus/RAG 기반 구축 (react-app-scaffold 컨벤션 → 내장 RAG)
**지금 요청**: 프로젝트 투입 후 **프로젝트-특화 규칙**이 추가될 때, 이를 체계적으로 관리하는 방안

이건 "초기 corpus는 고정 컨벤션이지만, 실제 프로젝트마다 새로운 함수/유틸/패턴이 생기면 그것도 규칙화해서 RAG에 먹여야 한다"는 문제입니다. 바로 설계해드릴게요.이제 전체 그림이 명확해졌습니다. 핵심 문제를 정확히 짚겠습니다.

**문제**: 초기 RAG는 react-app-scaffold 컨벤션 기반으로 잡혀있지만, 실제 프로젝트에 투입되면 `projectSpecificUtil.ts`, `useCustomAuth.ts` 같은 프로젝트-고유 코드들이 생겨납니다. 이것들도 "규칙"이 되어야 하는데, 누가 어떻게 그 규칙을 만들고 RAG에 먹일 것인지 방법이 없습니다.

전체 설계 방안을 문서로 만들어드리겠습니다.이제 전체 아키텍처를 시각화해드릴게요.전체 방안의 핵심 구조입니다.

## 핵심 설계 철학

문제의 본질은 "규칙을 어떻게 발견하느냐"입니다. 개발자가 명시적으로 문서화하지 않는 한 AI는 프로젝트-특화 규칙을 영원히 모릅니다. 그래서 **세 가지 발견 경로**를 만들었습니다.

**경로 A — 명시적 등록**: 개발자가 "이건 규칙이다"라고 알 때. 커맨드 팔레트로 직접 작성하거나 기존 파일을 규칙으로 변환합니다.

**경로 B — 자동 스캔**: 프로젝트 투입 초기에 `src/utils/`, `src/hooks/`를 전체 분석해서 scaffold 기본 corpus에 없는 패턴을 AI가 초안으로 뽑아줍니다. 이후에는 git 변경 파일만 증분 분석합니다.

**경로 C — 채팅 감지**: 가장 자연스러운 경로입니다. 개발자가 AI 제안을 거부하고 수정하거나 "여기선 ~써야 해"라고 말하는 순간을 감지해서 저장을 제안합니다.

## RAG 우선순위 계층이 핵심

세 경로 모두 `.axiom/project-corpus/rules/`에 저장되고, 기존 `HybridRagEngine`에 병합될 때 **anti-pattern이 최우선**입니다. "useEffect로 직접 fetch 금지" 같은 규칙이 scaffold 기본 문서보다 먼저 조회됩니다. 충돌 시 프로젝트-특화 규칙이 기본 컨벤션을 덮어씁니다.
