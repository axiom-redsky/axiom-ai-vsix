## 1. 배경과 문제의식

Axiom의 오프라인 모드는 "LLM을 쓸 수 없는 환경(폐쇄망·서버 미기동)에서도 프론트엔드
개발자에게 최대한 실질적인 도움을 준다"는 목적으로 설계됐다. 다른 AI 어시스턴트가
전부 LLM 연결을 전제하는 것과 다른, Axiom 고유의 차별점이다.

그런데 현재 오프라인 구조에는 구조적 한계가 하나 있다:

- **자연어 → 의도 분류(정규식/IntentSignals) → 바로 실행** 구조는 오분류가 곧
  사고가 된다 (modify→create 누수로 기존 파일 덮어쓰기 사례).
- 모델 없는 자연어 이해는 "프롬프트마다 엣지버그 무한"의 두더지잡기다
  ([intent-routing-collision-safety]에서 확정된 진단).
- 그래서 오프라인의 "행동(생성·수정)"을 자연어 실행에 그대로 맡기는 방향은
  구조적으로 정직하지 않다.

### 핵심 통찰 — 결정론 층은 이미 모델 없이 돈다

Axiom이 약한 sLLM을 보정하려고 쌓아온 층들 — locate, structural apply,
ScaffoldContracts 계약/레시피 카드, ComponentPropsIndex, 페이지 템플릿,
봉투계약 탐지기 — 은 **애초에 모델 없이 동작하는 코드**다. 파이프라인에서 모델이
실제로 맡는 건 ① 자연어 이해 ② 작은 판단 한 조각(필드 매핑, 후보 중 선택)뿐인
경우가 많다 (compose binding: "분해·대조는 결정론, 모델은 필드매핑 한 조각").

**→ 오프라인 모드 = 그 "모델의 한 조각"을 사람의 클릭(추천 카드·위저드·객관식)으로
치환한 도구 모음.** region disambiguation에서 "우선순위는 미리 알 수 없다 →
이해하는 쪽에 위임"이라 결론냈는데, 오프라인에서는 그 '이해하는 쪽'이 모델이 아니라
사용자 본인이 된다.

## 2. 핵심 설계 결정 (확정)

1. **자연어의 역할을 "실행"에서 "추천"으로 바꾼다.**
   입력창은 그대로 두되, 오프라인에서 행동성 요청은 바로 실행하지 않고
   **버튼이 달린 추천 카드**를 렌더하는 것까지만 자연어(정규식)가 담당한다.
   실행은 버튼 클릭 → QuickPick 위저드(결정론)가 이어받는다.
   - 오분류가 무해해진다: 틀려도 "엉뚱한 버튼이 하나 보일 뿐", 사용자가 다른
     버튼을 누르면 끝. 정규식 두더지잡기가 "추천 품질"이라는 저위험 문제로 격하.
   - 채팅 입력창이 "명령 실행기"에서 "검색창"으로 바뀌는 것 (유튜브 검색 비유:
     검색어를 쳐도 영상이 바로 재생되지 않고 결과 목록이 뜬다).

2. **Q&A와 행동을 분리한다.**
   - Q&A(지식 검색)는 오답 비용이 0이므로 **지금처럼 자연어 → 바로 답변** 유지
     (OfflineKnowledgeRetriever 그대로).
   - 행동(생성·수정)만 추천 카드를 거친다.

3. **행동 카탈로그는 코드가 아니라 데이터(카드)다.**
   트리거·슬롯·행동을 선언하는 카드 파일로 정의하고, 엔진(매칭→정렬→위저드→적용)은
   카드 내용을 모른다. ScaffoldContracts 카드·knowledge/_index 키워드·page-templates가
   이미 같은 "트리거 → 내용물" 패턴 — 이를 하나의 카드 스키마로 승격·통합하는 것.

4. **엔진은 프레임워크 중립, 지원은 React scaffold 전용 유지.**
   Vue/Next 지원을 지금 목표로 잡지 않는다 (Axiom의 경쟁력 = scaffold 계약에 깊이
   묶인 것, 특허 차별성 서사와 동일). 단, 엔진에 React 가정을 하드코딩하지 않아
   미래에 "카드 팩 추가"만으로 확장 가능한 구조를 공짜로 얻는다.

5. **자연어를 건너뛰는 입구를 함께 제공한다.**
   채팅창 `/` 자동완성(슬래시 커맨드), 런처 패널 고정 메뉴, VSCode 명령 팔레트 —
   전부 같은 위저드로 수렴. 숙련자는 이 길로 다닌다.

6. **추천 표시는 2형태 — A(채팅 카드)가 기반, B(입력창 위 리스트)가 최종형.** (2026-08-28 확정)
   - **형태 A** = Enter 후 응답으로 뜨는 채팅 메시지 카드. B가 생겨도 없앨 수 없다:
     이미 전송된 메시지의 회수처이자, 기록이 남고, 완료 카드→"다음 단계" 버튼 연쇄가
     대화 흐름 안에서만 성립하기 때문.
   - **형태 B** = 타이핑 중 입력창 위에 실시간으로 뜨는 자동완성형 리스트
     ("입력창=검색창"의 문자 그대로의 구현). 방향키+Enter로 위저드 직행.
   - 같은 매칭 엔진, 두 출구. 구현 순서 = A 먼저(기존 채팅 카드 포맷·"Enter→응답"
     흐름을 그대로 탐), B는 그 엔진 위에 표시 컴포넌트만 얹는 후속. §3.5 참조.

## 3. UI 흐름 (4장면)

### 장면 1 — 입력은 지금과 동일
```
┌─ Axiom Chat ────────────────────────────────┐
│  나: 직원 목록 페이지 만들어줘               │
└─────────────────────────────────────────────┘
```

### 장면 2 — 실행 대신 추천 카드 (여기가 바뀌는 지점)
기존 채팅 카드 포맷(banner/출처칩)과 같은 계열의 메시지 하나.
정규식 분류 결과는 **버튼 순서와 프리필**에만 반영된다.
```
┌─ Axiom Chat ────────────────────────────────┐
│  Axiom: ⚡ 오프라인 모드 — 이렇게 도와드릴 수 있어요: │
│  ┌─────────────────────────────────────┐    │
│  │ 📄 목록 페이지 생성 위저드           │    │
│  │    (list 유형으로 시작)       [열기] │    │
│  ├─────────────────────────────────────┤    │
│  │ 🔌 API → 테이블 바인딩 위저드 [열기] │    │
│  ├─────────────────────────────────────┤    │
│  │ 📚 관련 문서: list-page 가이드 [보기]│    │
│  └─────────────────────────────────────┘    │
└─────────────────────────────────────────────┘
```

### 장면 3 — 버튼 클릭 → QuickPick 위저드 (VSCode 네이티브 부품, 새 UI 아님)
```
1/3 도메인 선택      →  2/3 페이지 유형(list 프리필)  →  3/3 이름 입력
  ▸ main                  ▸ 목록 (list)                   EmployeeList▌
    example                 폼 (form)
    + 새 도메인             상세 (detail)
```
이 시점부터 자연어 해석은 0. page.template.txt + router.template.txt 결정론 생성.

### 장면 4 — 완료 카드 + 다음 행동 연결
```
┌─ Axiom Chat ────────────────────────────────┐
│  Axiom: ✅ 생성 완료                         │
│  · src/domains/main/pages/EmployeeList.tsx  │
│  · router.tsx 에 경로 배선됨                 │
│  다음 단계: [🔌 이 테이블에 API 바인딩] [📚 SmartTable 문서] │
└─────────────────────────────────────────────┘
```

### 3.5 추천 표시 2형태 (확정 2026-08-28)

장면 2(형태 A, 채팅 카드)는 **Enter 후**의 표시다. 최종형에서는 **Enter 전**,
타이핑 중에 입력창 위로 실시간 리스트(형태 B)가 함께 뜬다:

```
        ┌───────────────────────────────────────┐
        │ 📄 목록 페이지 생성 위저드      ↵ 선택 │
        │ 🔌 API → 테이블 바인딩 위저드          │
        │ 📚 list-page 가이드 문서               │
        ├───────────────────────────────────────┤
        │ Enter = 그냥 메시지로 보내기            │
        └───────────────────────────────────────┘
┌─ 입력 ─────────────────────────────────────────┐
│ 직원 목록 페이지▌                               │
└────────────────────────────────────────────────┘
```

| | 형태 B (입력창 위 리스트) | 형태 A (채팅 카드) |
|---|---|---|
| 시점 | Enter 전, 타이핑 중 | Enter 후, 응답으로 |
| 역할 | 빠른 진입·발견 (방향키+Enter 위저드 직행) | 놓친 경우 회수·기록·다음 단계 연쇄 |
| 구현 | 후속 (엔진 위에 표시 컴포넌트) | **기반 (Phase 1)** |

- 채팅 webview 입력창(`InputBar`)이 자체 React 컴포넌트라 B는 완전히 우리 통제하에
  구현 가능. `/` 슬래시 메뉴와 **같은 표시 컴포넌트를 공유**한다.
- 리스트를 무시하고 Enter로 전송하면 → 형태 A 카드로 회수 (두 형태는 대체가 아니라 보완).
- 매칭은 트리거 키워드 필터 수준이라 타이핑 중 실시간(디바운스) 부담 없음.

## 4. 행동 카드 파일 형식 (확정 2026-08-28)

**형식 = md + YAML frontmatter, 한 파일 = 카드 한 장** (`.axiom/actions/*.card.md`).
knowledge 문서 컨벤션과 일치하고, **frontmatter = 기계용 메타데이터 / 본문 = 사람용
설명 + 코드 골격**이라는 역할 분담이 자연스럽다. (json 단독안은 골격 코드를 문자열로
이스케이프해야 해서 기각.)

### 완전한 예시 — 프로젝트 카드 한 장

````markdown
---
schemaVersion: 1                  # 스키마 진화 대비
id: project-search-form           # 파일명과 일치 강제 (충돌 방지)
title: 표준 검색폼 삽입
icon: 🔍
triggers: [검색폼, 검색 조건, 조회 조건, search form]
preconditions: [file-open, scaffold-detected]
slots:
  - name: formName
    label: 폼 이름
    source: text                  # text | domain-list | endpoint-list | component-list
    prefillFrom: query
action:
  type: recipe                    # template | recipe | doc | command
priority: 20
---

## 설명 (패널·카드에 표시)
우리 프로젝트 표준 검색폼. Select+Input+조회버튼 골격.

## 골격 (recipe 타입일 때 — 슬롯 치환 후 structural apply로 삽입)
```tsx
const [{{formName}}Params, set{{formName}}Params] = useState<T{{formName}}Params>({});
...
```
````

### 형식 규칙 3가지 (계약)

1. **스키마 검증은 로드 시점, fail-open.** 필수 필드 누락·모르는 `action.type`·
   트리거 중복이 있으면 **그 카드만 비활성** + 패널에 ⚠ 표시(VSCode Problems 병행).
   잘못된 카드 하나가 카탈로그 전체를 죽이면 안 된다.
2. **`source` 어휘는 초기 4~5개로 한정.** `text` / `domain-list` / `endpoint-list` /
   `component-list` 수준. 슬롯 소스 = "위저드가 자동으로 채워줄 수 있는 것"의 목록이라
   여길 좁게 시작해야 카드 작성 난이도가 낮다. 확장은 스키마 버전과 함께.
3. **패널은 카드 파일을 건드리지 않는다.** 켜기/끄기 토글 상태는 카드 파일이 아니라
   **워크스페이스 설정(비활성 id 목록)**에 저장 — 파일은 git에서 항상 깨끗하게,
   "내가 껐다"는 개인 상태가 팀에 커밋되지 않게.

### 매칭 엔진

- `action.type` 종류: `template`(파일 생성), `recipe`(structural 삽입 —
  기존 레시피 카드 실행), `doc`(지식문서 렌더), `command`(위저드/명령 호출).
- 질문 토큰 vs triggers — **유한 카탈로그에 대한 검색 문제**이므로 기존 오프라인
  검색 교훈(복합키워드·공백변형 정밀화, [offline-retrieval-ranking])을 그대로 적용.
  상위 N개(2~3장)만 노출.
- 한글 트리거 주의: 정규식 `\b`는 한글에 안 먹음 ([scaffold-contract-coverage] 함정).

## 5. 카탈로그 3계층 + 관리 UI

| 계층 | 위치 | 관리 주체 | 용도 |
|---|---|---|---|
| 내장 카드 | 익스텐션 번들 | Axiom | scaffold 핵심 (페이지 위저드·API 바인딩·레시피) |
| **프로젝트 카드** | `.axiom/actions/` — **git 커밋으로 팀 공유** | 프로젝트 리더/선임 | 업무별 표준 레시피 ("우리 프로젝트 검색폼 카드") |
| 개인 카드 | globalStorage | 개인 | 개인 취향 스니펫 |

폐쇄망 SI 팀에서 프로젝트 계층이 특히 강력: 선임이 카드를 등록해 커밋하면 팀 전체가
같은 추천을 받는다. `.axiom/knowledge` 핫리로드(_AUTHORING 워크플로우)와 같은
메커니즘을 `.axiom/actions/`로 확장.

### 관리 UI 원칙 — "편집은 파일, 관리는 패널"
사용자가 개발자이므로 처음부터 폼 편집기를 만들지 않는다.
- **편집** = 카드 파일 직접 작성 (`.card.md`, §4 형식, 저장 즉시 핫리로드)
- **관리 패널** 기능:
  - 카드 목록 (계층별·활성 여부·검증 ⚠ 표시)
  - 켜기/끄기 토글 (삭제 대신 비활성화 — 상태는 워크스페이스 설정에, §4 규칙 3)
  - "새 카드 만들기" (템플릿 스캐폴딩)
  - 카드 lint (트리거 중복·슬롯 오류 검사)
  - **드라이런**: "이 카드가 어떤 질문에 뜨는지" 미리보기 — 트리거 겹침으로
    엉뚱한 카드가 위로 오는 문제(오프라인 top-N 오염과 같은 부류)를 등록 시점에 차단

## 6. 카드 채집 플라이휠 (등록 자동화)

등록을 전부 수작업에 두지 않는다: **온라인 모드에서 LLM이 성공적으로 해낸 편집**
(applied + 미되돌림)을 감지하면 "이 패턴을 오프라인 레시피 카드로 저장할까요?"
제안. RegionCaptureRecorder 포집 인프라(요청·적용 결과 JSONL)가 원료를 이미 보유.

→ 카탈로그가 팀의 실제 업무를 따라 자라고, **온라인 사용이 오프라인 자산을 만드는**
플라이휠. "LLM 없는 환경 대비"라는 Axiom 설계 철학의 대표 서사가 될 수 있음
(특허/발표 서사에도 얹기 좋은 조각).

## 9. 단계별 실행 계획 (초안)

- **Phase 0 — 카드 스키마 + 매칭 엔진 (기반)**
  카드 타입 정의, 내장 카드 3~4장(수기), 트리거 매칭·정렬. 테스트: 카드 드라이런
  하니스(질문 → 뜨는 카드 top-N 스냅샷, eval:region 계기판과 동형 철학).
- **Phase 1 — 추천 카드 UI(형태 A) + 페이지 위저드 (A2)**
  오프라인 행동성 요청 → 채팅 카드 렌더(기존 카드 포맷 확장) → QuickPick 위저드 →
  템플릿 생성. 기존 오프라인 실행 경로는 카드 뒤로 이동(직접 실행 제거).
- **Phase 2 — API 바인딩 위저드 (A1)**
  compose binding 오프라인 변형: 필드 매핑 테이블 UI.
- **Phase 3 — 카탈로그 3계층 + 관리 패널**
  `.axiom/actions/` 핫리로드, 목록/토글/새 카드/lint/드라이런 패널.
- **Phase 4 — 확장**
  입력창 위 실시간 추천 리스트(형태 B, §3.5 — `/` 슬래시 메뉴와 표시 컴포넌트 공유),
  Scaffold 린트(C1, 독립 트랙으로 병행 가능), 카탈로그 패널(B1), 채집 플라이휠(§6).

각 Phase 완료 기준: 기존 테스트 무회귀 + 해당 기능 전용 테스트 green
(오프라인 개선 시 공유 어휘스코어러 buildContext 절대 수정 금지 원칙 유지).

## 10. 리스크·미결정 사항

1. **온라인 모드와의 UX 이원화**: 온라인=자연어 실행, 오프라인=카드 경유의 이질감.
   → 완화: 카드 패턴이 검증되면 온라인의 "실행은 충돌 안전(되묻기)" 처방에 역수입
   가능 (오프라인이 선행 실험장).
2. **카드 매칭 품질**: 유한 카탈로그 검색이라 자연어 실행보다 훨씬 쉽지만,
   트리거 겹침·한글 토큰화는 여전한 주의 지점. → 드라이런·lint로 등록 시점 차단.
3. ~~카드 스키마 형식~~ → **해소 (2026-08-28)**: md + YAML frontmatter 확정, §4.
4. **슬롯 소스 표준화**: 초기 4~5개 한정 원칙은 확정(§4 규칙 2), 정확한 목록과
   각 소스의 스캔 계약(무엇을 어디서 어떻게 긁나)은 Phase 0에서 확정.
5. **채집 플라이휠의 일반화 품질**: 성공 편집 → 카드 변환 시 "그 파일 전용"이 아닌
   재사용 가능한 골격으로 추상화하는 규칙 필요 (수동 확인 단계를 거치는 반자동이 안전).
