1결론 요약

"Axiom 특허가 어렵다"는 결론이 아니다. "넓은 특허는 사실상 불가능하고, 좁은 특허는 충분히 가능하다"가 정확한 결론이다.

중국 문헌 CN 122195419 A를 청구항 단위로 정밀 대조한 결과, 이 문헌은 Axiom의 특허 본진(코드 적용·검증 계층)과 접촉면이 없다. 침해 리스크는 매우 낮고(all-elements 미충족 + 중국 내 효력), 3층 청구항의 인용문헌으로 쓰기도 어렵다.

진짜 위험 요소는 이 문헌이 아니라 GitHub 공개에 따른 공지예외 유예기간이다. 국가별로 유예 제도가 달라 중국·유럽 출원은 이미 닫혔다고 보아야 하며, 한국의 잔여 기간 확인이 가장 급하다.

특허로 살아남을 확률이 가장 높은 부분은 StructuralAnchor 기반 리전 편집 계층이며, 그중에서도 "약한 모델 출력의 실패모드별 결정론 교정 + 검증 폐루프"가 선행기술이 가장 덜 밟은 땅이다.

2층별 진단 — 3층 구조 분석

Axiom을 세 층으로 나누면 특허성 판정이 층마다 갈린다.

1층 — 컨셉층 사실상 포기

"폐쇄망에서 로컬 LLM + 벡터DB로 코딩을 보조한다"는 층이다. Continue, Tabby, PrivateGPT 계열과 로컬 RAG 논문 다수, 그리고 이번 중국 문헌까지 전부 선행기술이다. 이 층에 청구항을 걸면 거절이 확실하므로 예산과 미련을 두지 않는다.

2층 — 리트리벌 파이프라인 조건부 생존

centroid 라우팅 + RRF + reranker 게이팅. 각 요소는 전부 기성품이다(RRF는 논문 발표 후 20년 가까이 경과, reranker 게이팅도 일반적). 조합만으로는 진보성이 약하다. 다만 은행 표준단어·표준용어·표준도메인이라는 특정 데이터 구조와 결합하면 — 예: "메타데이터 필드 태깅을 라우팅 기준으로 사용" — 심사관이 인용할 수 있는 문헌이 급감한다. 넓게 쓰면 죽고, 은행 메타데이터에 묶으면 산다.

3층 — StructuralAnchor 리전 편집 특허 본진

특허 심사는 "문제 → 수단 → 효과"가 구체적으로 맞물릴 때 통과되는데, 이 층이 유일하게 세 요건을 자력으로 충족한다.

  • 문제가 구체적 — 로컬 소형 모델은 파일 전체를 다시 출력하지 못한다.
  • 수단이 구체적 — 구조적 앵커로 편집 영역을 특정해 해당 구간만 교체한다.
  • 효과가 측정 가능 — 토큰 소모, 적용률(계기판 기준 33%→84%), 컨텍스트 초과 실패율.

약 1,700줄 규모의 src/ai/apply/StructuralAnchor.ts 구현체가 그 자체로 실시 근거가 된다.

3.3 결정적 차이 — "적용(apply) 계층"의 부재

문헌 전체를 훑어도 생성된 코드를 파일에 적용하는 단계가 단 한 줄도 없다. 모델 응답은 터미널에 출력되고 끝난다(【0043】). 즉:

  • 구조적 앵커로 편집 영역을 특정하는 것 — 없음
  • 모델 출력의 실패모드를 교정하는 것 — 없음
  • tsc 검증-교정 폐루프 — 없음
  • 편집 결과의 정합성 보장 — 개념 자체가 없음

Axiom의 본진(3층: StructuralAnchor + 결정론 교정기 + verify-correct 루프)은 이 문헌과 접촉면이 0이다. "코드 조각을 생성한다"까지는 같지만, 이 특허의 세계는 생성에서 끝나고 Axiom의 세계는 생성 이후부터 시작한다.

3.4 가장 가까운 접점 — 그리고 왜 다른가

유일하게 닮은 부분은 S4의 "2차원 매칭"(키워드 매칭 실패 시 임베딩 유사도 폴백)으로, Axiom의 의도 라우팅과 표면적으로 유사하다. 그러나:

  • 목적이 다름 — 저쪽은 "OS 튜닝 도구를 부를까 말까"의 이진 트리거, Axiom은 수정/생성/질문/페이지생성 등 다중 의도 분류 후 편집 파이프라인 라우팅
  • 수단이 다름 — 저쪽은 사전 구축된 트리거 KB와의 코사인 임계값(0.9), Axiom은 LLM 위임 분류(IntentClassifier) + 정규식 폴백 + 충돌 안전 되묻기

이 접점조차 청구항 1의 다른 필수 요소(S1의 파인튜닝·GGUF)가 Axiom에 없으므로 침해 구성이 되지 않는다.

3.5 종합 판정 — 두 관점

① 침해 리스크 관점 (Axiom이 이 특허를 밟는가): 매우 낮음

  • 청구항 1의 필수 요소 S1(자체 파인튜닝+GGUF 제작)과 S4(OS 튜닝 도구 호출)를 Axiom은 수행하지 않음 → all-elements 기준 미충족
  • 중국 출원이므로 효력 범위는 중국 내 — 한국 사업에는 애초에 미치지 않음

② 선행기술 관점 (Axiom 출원 시 인용될 것인가):

  • 1층 — "로컬 경량모델 + 로컬 RAG + 구조화 프롬프트로 개발 보조"의 공지 재확인. 사망 판정 유지
  • 2층 — 일반형 RAG(milvus+ANN+스티칭)가 공지됐으니, 은행 표준 메타데이터 결합 없는 일반 청구항은 더 위험해짐
  • 3층 — 편집·적용·검증 영역에 아무 개시가 없어 인용문헌으로 쓰기 어려움. "②+④ 뼈대 + ① 환경" 전략이 이 문헌으로 오히려 지지됨
시간관계 부수사항 — 이 출원의 출원일은 2026-03-13. 만약 Axiom의 GitHub 공개가 그보다 앞선다면, 반대로 Axiom의 공개가 이 출원의 선행기술이 되는 관계다(그들의 중국 심사에서). 공지예외 기산점 확인과 함께 시간관계를 대리인에게 전달할 가치가 있다.

4핵심 차별 명제

차별점은 "무엇을 하느냐(what)"가 아니라 "어떻게 신뢰성을 확보하느냐(how)"에 있다. 한 문장으로 압축하면:

약한 로컬 소형모델을 신뢰 가능한 코드 편집기로 만들기 위해, "결정론(확장) / 확률(모델)"을 특정 방식으로 분업시키는 아키텍처.

Continue·Tabby·PrivateGPT 계열 선행기술은 전부 "모델에게 맡기고 결과를 받는" 구조로, 모델이 강하다는 전제 위에 서 있다. Axiom의 전제는 정반대다 — "모델은 약하다. 그러므로 모델이 하는 일을 한 조각으로 좁히고, 위치 결정·검증·교정은 확장이 결정론으로 처리한다." 이 전도된 전제가 코드 전반에 일관되게 구현되어 있으며, 이것이 선행기술과 갈라지는 지점이다. 모델을 신뢰하는 전제에서는 아래 5절의 장치들이 애초에 필요하지 않기 때문이다.

5청구항 재료 — 구체 기술수단 4종

추상 명제만으로는 청구항이 성립하지 않는다. 아래 구체 수단들이 실제 코드로 존재한다.

① 구조적 앵커 기반 부분편집

  • splitTsSections가 소스를 import / 컴포넌트 / 섹션 단위로 결정론적으로 분해하고, computeAnchors가 삽입·교체 지점을 특정한다 (StructuralAnchor.ts:287).
  • 모델은 그 안에 들어갈 조각(hookCode)만 생성한다 — 파일 전체 재출력을 요구하지 않는다.
  • "파일 전체 재출력 불가"라는 소형모델 고유 문제의 직접 해법이다.

주의: ① 단독은 완전 신규가 아니다. LSP/AST 기반 부분편집, tree-sitter 범위 편집 등의 선행기술이 존재한다. 따라서 ①은 청구항의 뼈대가 아니라 실행환경(전제부)으로 배치하는 것이 안전하다(7절).

② 생성물의 결정론적 사후 정합 — 가장 덜 밟힌 땅

모델 출력을 그대로 적용하지 않고, 소형모델의 전형적 실패모드를 열거한 뒤 각각에 전용 결정론 교정기를 붙였다. 이 "실패모드 열거 + 교정기" 구조는 좁은 청구항으로 쓰기에 적합하다. CN 122195419 A를 포함한 검토 선행기술 어디에도 이 영역의 개시가 없다.

소형모델 실패모드결정론 교정기
훅 조각 안에 import를 섞어 냄 → 함수 중간에 import가 박혀 컴파일 에러extractImportsFromHookCode — import를 파일 상단 채널로 hoist

③ 트리거 기반 계약 자동주입 (ScaffoldContracts)

프로젝트 스캐폴드 특유의 계약(useApi 봉투 구조, 라우터, 타입 규약 등 11종 계약 카드)을 트리거 단어로 감지해 프롬프트에 자동 주입한다. 2층 전략의 "도메인 결합" 논리와 정확히 맞물린다 — 특정 스캐폴드/표준 구조에 묶을수록 인용문헌이 줄어든다.

④ 검증-교정 폐루프 (Verify-Correct Loop)

편집 결과를 임시 형제파일로 만들어 tsc 진단(VSCode getDiagnostics)으로 검증하고, 실패 시 앵커 기반 <replace> 교정을 1회 수행한 뒤 fail-open 한다. 선행기술의 open-loop one-shot 구조와 대비되는 폐루프(closed-loop)다.

검토된 중국 문헌은 1층(컨셉층)을 커버할 뿐, ②·④의 영역에는 도달하지 않는다. 모델을 신뢰하는 전제에서는 필요가 없는 장치들이기 때문이다.

7청구항 전략 제안

  • 뼈대 = ②+④ — "약한 모델 출력의 실패모드별 결정론 교정 + 폐루프 검증". ① 단독이면 AST 편집 선행기술과 정면충돌하지만, 이 문제설정은 덜 밟힌 땅이라 인용할 문헌이 드물다.
  • ① = 실행환경(전제부)으로 배치 — "로컬 소형모델 + 폐쇄망 제약 하에서 구조적 앵커 부분편집을 수행하는 시스템에 있어서…" 형태로, 조합의 구체성을 만드는 한정 요소로 쓴다.
  • 2순위 = ③ + 은행 표준 메타데이터 — 메타데이터 필드 태깅을 라우팅 기준으로 쓰는 도메인 결합형 리트리벌을 별건으로 검토한다.

8최우선 리스크 — 공지예외 유예기간

공지예외(신규성 상실의 예외) 제도는 국가마다 다르며, GitHub 공개는 이미 발생한 사실이다.

9영업(피치) 관점의 특허 포지셔닝

금융권 SI RFP에서 등록특허와 출원중의 실질 차이는 크지 않다. "특허 출원 중" 한 줄이 평가표에서 수행하는 역할은 대부분 "자체 기술 보유"의 증명이지, 경쟁사 차단이 아니다.

Continue+Ollama 조합과 경쟁할 때 실제로 이기는 무기는 특허가 아니라 은행 표준 메타데이터 파이프라인과 폐쇄망 실증 레퍼런스다. 따라서 특허는 "울타리"가 아니라 "간판"으로 기대하는 것이 현실적이며, 실질 방어의 본체는 기존 결론대로 영업비밀 + EULA 강화다. 특허는 그 위에 얹는 신뢰 장치다.

10액션 아이템

  1. 공지예외 잔여기간 즉시 확인 — GitHub 공개 시점 기산을 대리인과 확정. 모든 전략이 이 답에 종속된다. (최우선)
  2. 컨셉층(1층) 청구항 폐기 — 예산과 미련을 두지 않는다.
  3. ②+④ 뼈대 + ① 실행환경 구성으로 1건 제대로 출원 — StructuralAnchor 계열에 집중.
  4. 은행 메타데이터 RAG(②층+③)는 도메인 결합형으로 2순위 별건 검토.
  5. CN 122195419 A와의 시간관계를 대리인에게 전달 — 출원일 2026-03-13 vs Axiom GitHub 공개일의 선후 확인.
  6. 방어 본체는 영업비밀 + 계약(EULA) 유지 — 특허는 간판으로 운용.
