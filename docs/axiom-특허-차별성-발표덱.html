05 · 중국 문헌 정밀 대조

결정적 차이 — 이 특허에는
"적용(apply) 계층"이 없다

모델 응답은 터미널에 출력되고 끝난다.
이 특허의 세계는 생성에서 끝나고, Axiom의 세계는 생성 이후부터 시작한다. 문헌 전체에 "생성된 코드를 파일에 적용하는 단계"가 단 한 줄도 없음 — 구조 앵커 편집·실패모드 교정·tsc 폐루프·정합성 보장 전부 무개시.
가장 가까운 접점 하나

S4의 "2차원 매칭"(키워드 실패 시 임베딩 폴백)이 Axiom 의도 라우팅과 표면 유사. 그러나 목적이 다르고(OS튜닝 이진 트리거 vs 다중 의도 분류→편집 라우팅) 수단이 다르다(트리거 KB 코사인 임계값 vs LLM 위임 분류+정규식 폴백+되묻기).

시간관계 부수사항

이 출원의 출원일은 2026-03-13. Axiom의 GitHub 공개가 그보다 앞선다면, 반대로 Axiom 공개가 이 출원의 선행기술이 되는 관계. 대리인에게 시간관계를 함께 전달할 가치가 있다.

06 · 중국 문헌 정밀 대조

종합 판정 — 두 관점

① 침해 리스크: 매우 낮음

청구항 1의 필수 요소 S1(자체 파인튜닝+GGUF 제작)과 S4(OS 튜닝 도구 호출)를 Axiom은 수행하지 않음 → all-elements 기준 미충족.

게다가 중국 출원이므로 효력 범위는 중국 내 — 한국 사업에는 애초에 미치지 않음.

② 선행기술 영향: 3층 무접촉

1층 — "로컬 경량모델+RAG 개발보조" 공지 재확인, 사망 판정 유지.
2층 — 일반형 RAG(milvus+ANN+스티칭)가 공지됐으니 은행 메타데이터 결합 없는 일반 청구항은 더 위험.
3층 — 편집·적용·검증 영역 무개시. "②+④ 뼈대 + ① 환경" 전략이 이 문헌으로 오히려 지지됨.

07 · 핵심 차별 명제

선행기술과 갈라지는 지점은
기능이 아니라 전제다

"모델은 약하다. 그러므로 모델에게는 한 조각만 시키고,
위치 결정·검증·교정은 확장이 결정론으로 수행한다." Continue·Tabby 계열은 정반대 — "모델은 강하다, 맡기고 결과를 받는다." 이 전도된 전제가 코드 전반에 일관되게 구현되어 있다.
선행기술의 전제

강한 모델 → 파일/패치 통째 생성 → 품질은 모델에 의존 → 검증 장치가 애초에 불필요

Axiom의 전제

약한 로컬 소형모델 → 조각만 생성 → 실패모드를 열거하고 각각에 결정론 교정기 → 폐루프 검증

08 · 청구항 재료 ①

구조적 앵커 기반 부분편집

  • a소스를 결정론적으로 분해 — splitTsSections가 import / 컴포넌트 / 섹션 단위로 파일을 해부하고 computeAnchors가 삽입·교체 지점을 특정StructuralAnchor.ts:287 — 위치 결정은 100% 확장 몫
  • b모델은 조각(hookCode)만 생성 — 파일 전체 재출력을 요구하지 않음"소형모델은 파일 전체를 다시 뱉지 못한다"는 고유 문제의 직접 해법
  • c효과가 수치로 측정됨 — 토큰 소모, 적용률(33%→84%), 컨텍스트 초과 실패율eval 하니스로 재현 가능한 정량 효과 — 명세서 실시예 재료

⚠ 단독으로는 완전 신규가 아님 — LSP/AST·tree-sitter 기반 부분편집 선행기술 존재. ①은 뼈대가 아니라 실행환경으로 배치하는 것이 안전.

09 · 청구항 재료 ② — 가장 덜 밟힌 땅

실패모드 열거 + 결정론 교정기

모델 출력을 그대로 적용하지 않는다. 소형모델의 전형적 실패모드마다 전용 교정기가 붙어 있다 — 전부 실제 코드로 존재.

소형모델 실패모드결정론 교정기 (실제 함수)
훅 조각 안에 import를 섞어 냄 → 함수 중간에 import 박힘extractImportsFromHookCode — 상단 채널로 hoist
이미 있는 state/훅을 중복 선언findDuplicateDeclarations
선언 없는 심볼 참조findUnresolvedReferences + resolveKnownImports
JSX 컴포넌트 import 누락findUnresolvedJsxComponents + ensureUiComponentImports
엔드포인트를 별칭·환각으로 교체normalizeEndpointExpr — 별칭 해소 후 동일성 판정
닫는 태그를 조용히 삭제closer-dropped 가드 → full 폴백

모델을 신뢰하는 전제에선 애초에 필요가 없는 장치들 — 그래서 선행기술이 거의 갖고 있지 않다. 중국 문헌도 이 영역에 아무 개시가 없음.

10 · 청구항 재료 ③ ④

계약 자동주입 + 검증-교정 폐루프

③ ScaffoldContracts

트리거 기반 계약 카드 자동주입

스캐폴드 특유의 계약(useApi 봉투 구조, 라우터, 타입 규약)을 트리거 단어로 감지해 프롬프트에 카드로 주입. 11종 계약 카드 운용 중.

2층 전략과 맞물림 — 특정 스캐폴드/표준 구조에 묶을수록 인용문헌이 줄어든다.

④ Verify-Correct Loop

tsc 진단 기반 폐루프 교정

편집 결과를 임시 형제파일로 tsc 검증(VSCode getDiagnostics) → 실패 시 앵커 기반 <replace> 교정 1회 → fail-open.

선행기술의 open-loop one-shot과 대비되는 폐루프(closed-loop) 구조.

12 · 청구항 전략

뼈대는 ②+④, ①은 실행환경으로

  • 뼈대②+④ — "약한 모델 출력의 실패모드별 결정론 교정 + 폐루프 검증"문제설정 자체가 덜 밟힌 땅. ① 단독이면 AST 편집 선행기술과 정면충돌하지만, 이 구성은 인용할 문헌이 드물다.
  • 환경① 구조적 앵커 부분편집 — 청구항의 실행환경(전제부)으로 배치"로컬 소형모델 + 폐쇄망 제약 하에서"라는 한정과 함께 조합의 구체성을 만든다.
  • 2순위③+은행 표준 메타데이터 — 도메인 결합형 리트리벌로 별건 검토메타데이터 필드 태깅을 라우팅 기준으로 쓰는 구조. 넓게 쓰면 죽고, 은행 데이터 구조에 묶으면 산다.

14 · 영업 관점

특허는 "울타리"가 아니라 "간판"이다

냉정한 현실

금융권 SI RFP에서 등록특허와 출원중의 실질 차이는 작다. "특허 출원 중" 한 줄이 평가표에서 하는 일은 "자체 기술 보유"의 증명이지, 경쟁사 차단이 아니다.

실제 이기는 무기

Continue+Ollama 조합과 붙을 때 승부처는 특허가 아니라 은행 표준 메타데이터 파이프라인과 폐쇄망 실증 레퍼런스다.

실질 방어의 본체는 기존 결론대로 영업비밀 + EULA 강화. 특허는 그 위에 얹는 신뢰 장치.
