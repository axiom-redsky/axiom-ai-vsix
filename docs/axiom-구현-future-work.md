## T1. 카드 출처 파이프라인 — 수기 저작 탈피 + 지식 소스 추상화

**해결할 질문**: "이 카드는 누가 만들고 어떻게 최신으로 유지되나?" — 지금은 답이 "확장 코드에 사람이 써넣음"이라 약함.

### 현재 상태

- ScaffoldContracts 계약 카드 11종: **확장 코드에 수기 저작·하드코딩**. scaffold가 바뀌면 사람이 카드를 고쳐야 함(드리프트 위험).
- ComponentPropsIndex(53컴포넌트): `build-component-props.mjs`가 scaffold `types.ts`에서 **자동 생성** — 소스 파생 파이프라인의 유일한 실존 선례.
- 고객사 표준용어집 주입: **미구현**. 표준단어/용어/도메인 통합은 탐색 단계.
- 카드 주입 계층의 소스 추상화 여부: **미확인** — 착수 시 첫 조사 항목.

### 작업 항목

**T1-a. 카드 소스 인터페이스(추상화 계층) 신설**
- [ ] 현행 카드 주입 경로 조사: ScaffoldContracts가 scaffold 전용 하드코딩인지, 소스를 갈아끼울 수 있는 구조인지 (`buildContractSection` 및 트리거 레지스트리).
- [ ] 카드 공급원을 인터페이스로 분리: `(트리거 감지) → (카드 소스 N개 질의) → (주입)`. 기존 수기 카드는 "내장 소스" 하나로 강등. 신규 소스(파생 카드·용어집 카드)가 같은 인터페이스로 꽂히게.
- [ ] 카드 충돌/우선순위 규칙(내장 vs 파생 vs 고객사) 정의 — 기존 smart-table-binding 양보 로직처럼 명시적으로.

**T1-b. Scaffold 파생 자동 갱신 (single source of truth)**
- [ ] build-component-props.mjs 패턴을 계약 카드로 확장: useApi/router/type 시그니처를 scaffold 소스(`C:\redsky\work\react\single_react_new_nicfirst\react-app-scaffold`)에서 추출해 카드 골격 생성 또는 최소한 **드리프트 검증**(카드 내용 vs 실소스 시그니처 대조, 불일치 시 빌드 경고).
- [ ] 전면 자동 생성이 위험하면 절충: 카드 본문은 수기 유지 + **시그니처·엔드포인트·prop 슬롯만 파생 데이터로 치환**하는 템플릿 방식.
- [ ] ⚠ 함정 기록: knowledge/use-api.md가 봉투 계약을 빠뜨려 모델·개발자 모두 오판했던 전례([compose-binding 트랙]) — 파생 파이프라인이 있었다면 예방됐을 부류의 결함. 드리프트 검증의 근거 사례로 활용.

**T1-c. 고객사 표준용어집 → 카드 주입 (신규 지식 소스 1호)**
- [ ] 용어집 입력 포맷 정의(csv/md/json — "고객=`customer`, 부서=`department`" 매핑 + 도메인 분류). `.axiom/` 폴더 배치 + 핫리로드(기존 `.axiom/knowledge` 핫리로드 선례 재사용).
- [ ] 트리거: 요청문에 한글 업무 용어 감지 → 해당 표준 영문 식별자 매핑 카드 주입. ⚠ 한글엔 정규식 `\b` 안 먹음(계약카드 트랙에서 확인된 함정) — 토큰화 기반 매칭 필요.
- [ ] 생성 후 결정론 검사(선택): 생성 코드의 식별자가 용어집 표준과 다르면 교정 또는 경고 — "표준을 강제함" 스토리의 실체. 기존 게이트(의존성·중복 선언 게이트)와 같은 후처리 계층에 배치.
- [ ] 검증: 용어집 유/무 각각에서 동일 요청 비교하는 테스트 + 실 sLLM 라이브 프로브(프롬프트 변경은 실모델로만 검증 — 기존 원칙).

## T2. 검증-교정 루프 fail-safe 계약 명문화

**해결할 질문**: "왜 교정이 한 번뿐인가?" → "무한 재시도는 GPU 낭비·드리프트 유발. 안 되면 **원본 보존하고 안전하게 멈춘다**"가 코드·테스트로 보장되는 사실이어야 함.

### 현재 상태

- Stage 0 verify-correct 루프 구현됨(`experimental.regionVerify`): tsc 진단 임시 형제파일, fail-open, 1회 `<replace>` 앵커 교정. **실모델 검증 대기** 상태.
- REJECT→원본 유지 로직은 각 게이트에 산재 — "실패 시 원본 무손상"이 단일 불변식으로 테스트되고 있지는 않음(확인 필요).

### 작업 항목

- [ ] 불변식 테스트 추가: 교정 1회 실패·게이트 REJECT·검증 예외(fail-open) 등 모든 실패 경로에서 **대상 파일 바이트 무변경**을 직접 단언하는 테스트 묶음.
- [ ] 재시도 상한을 상수/설정으로 명문화(현 1회) + 주석으로 설계 의도(bounded retry, 드리프트 방지) 기록.
- [ ] 실패 시 사용자 채팅 메시지 정비: "적용 실패" 뉘앙스가 아니라 "검사를 통과하지 못해 **원본을 보존**했습니다 (파일 무변경)"로 — 순수 Q&A 헛경고 제거했던 것과 같은 계열의 UX 작업.
- [ ] regionVerify 실모델 라이브 검증 완료 후 기본 ON 승격 판단.

## T4. 감사·거버넌스 영속 로그 ★ 최우선 신규 계층

**목표**: **"누가 · 언제 · 무엇을 AI에 요청 → AI가 무엇을 생성 → 누가 승인했나"가 전부 영속 로그로 남는다.** 세션 단위 diff/되돌리기를 넘어 감리·감사가 요구하는 영속 기록으로.

### 원리 (재현성의 올바른 자리)

- Axiom의 **결정**(locate, 게이트, 카드 주입, patch 적용 위치)은 결정론 → 로그로 **재현 가능**.
- sLLM **생성**은 비결정론 → 재현을 약속하지 않고 **원문 그대로 보존**(요청 프롬프트·모델 원출력·적용 diff).
- 즉 감사 만족의 수단은 재현이 아니라 **기록**. 스키마 설계 시 이 구분을 필드로 반영(결정 트레이스 vs 생성 원문).

### 현재 상태 (씨앗)

- RegionCaptureRecorder: 순수 모듈, 로컬 JSONL 포집, redaction 3단(full/skeleton/meta), ChatViewProvider 배선(globalStorage), 설정 3개 기본 OFF, 텔레메트리 아님·네트워크 0·폐쇄망 안전. **단 용도가 "실패 포집(플라이휠 연료)"** — 감사 목적 아님. 회수경로·변환도 미구현.
- region 편집이 deterministic patch 기반이라 "무엇이 어떻게 적용됐나"의 근거 데이터는 파이프라인에 이미 존재.
- **"누가 승인했나"(승인 이벤트) 기록: 전무.**

### 작업 항목

- [ ] **감사 이벤트 스키마 정의**: `{ 사용자(OS 계정/git user), 시각, 요청 원문, 주입 컨텍스트 요약(카드·참조파일), 모델 식별자, 모델 원출력(원문), Axiom 결정 트레이스(의도분류→locate→게이트 판정), 적용 diff, 결과(applied/rejected/원본보존), 승인 이벤트 }`.
- [ ] **승인 이벤트 포착**: 적용 확정 UX 지점(diff 승인/적용 버튼)을 "승인"으로 기록. 자동 적용 경로가 있다면 감사 모드에서는 명시 승인 단계를 거치게 할지 결정(정책 설정).
- [ ] **영속 저장소**: RegionCaptureRecorder를 확장 또는 병행 신설(포집 목적이 달라 스키마 분리 권장 — 실패 포집=redaction 강함 / 감사=원문 보존이 목적이라 방향이 정반대). 워크스페이스 로컬 JSONL + 회전(rotation)·보존기간 설정. 네트워크 0 유지.
- [ ] **무결성(선택, 감리 대응 강화)**: append-only + 레코드 해시 체인으로 사후 변조 탐지 가능하게.
- [ ] **회수/열람 경로**: 감리 제출용 내보내기(기간 필터, 사람이 읽는 형태 렌더) — 포집≠회수 원칙 유지(반출은 항상 수동·명시적).
- [ ] **설정과 기본값**: 감사 모드 토글(기본 OFF 시작), redaction 수준, 보존기간. 기존 실패 포집 설정과 혼동 없게 네이밍 분리.
- [ ] **테스트**: 스키마 단위 테스트 + 요청→생성→승인→로그 e2e(record/replay 하니스 재사용 검토).
