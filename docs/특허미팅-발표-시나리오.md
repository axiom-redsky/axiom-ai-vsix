# 변리사 미팅 발표 시나리오 — Axiom AI 특허출원 상담

> 대상 파일: `docs/Axiom-AI-특허출원-미팅자료-재구성.pptx` (총 29장, 도식 8장 포함)
> 흐름: **만든 것 → 왜 만들었나 → 해결 아이디어 → 어떻게 동작하나 → 뭐가 새로운가 → 특허 관점 → 여쭤볼 것**
> 권장 시간: 30~40분 (설명 20~25분 + 질의 10~15분)

## 시작 전 — 30초 요약 (엘리베이터 피치)

> "은행 같은 폐쇄망에서는 ChatGPT 같은 외부 AI를 못 쓰고, 사내에 설치하는 작은 AI는 코드를 통째로 고치게 하면 사고를 냅니다. 저는 **'고칠 곳과 검사는 프로그램이 책임지고, AI는 코드 조각 하나만 쓰게 하는'** 방식으로 이 문제를 풀었고, 실제로 동작하는 제품이 있습니다. 이 방식이 특허가 될 수 있는지 상담드리러 왔습니다."

## 슬라이드별 발표 대본

### 1장 — 표지
- "Axiom AI라는 개발 도구에 대한 특허 상담 자료입니다. 한 줄로 말씀드리면 — 인터넷이 차단된 보안망 안에서, 작은 AI로 코드를 안전하게 고치는 기술입니다."

### 2장 — 오늘 드릴 말씀은 세 가지입니다
- 세 박스를 그대로 읽으면 됩니다: 무엇을 만들었나 / 무엇이 새로운가 / 무엇을 여쭙고 싶은가.
- "전문용어 없이 쉬운 말로 설명드리고, 필요하면 상세 도식도 준비했습니다."

### 3장 — 저희가 만든 것, Axiom AI
- "코드 편집기 안에서 채팅으로 '검색 버튼 하나 추가해줘'라고 말하면 코드를 대신 고쳐 주는 도우미입니다."
- 흐름도를 손으로 짚으며: "개발자가 지시하면, 가운데의 Axiom(본 발명)이 관리·감독하고, 사내의 작은 AI는 코드 조각만 씁니다."
- 하단 배너: "전 기능이 실제로 완성되어 돌아가고, 자동 테스트가 220건 이상입니다." ← 실시예 근거가 있다는 신호.

### 4장 — 다만, 처한 환경이 다릅니다
- "금융·공공기관은 보안 때문에 인터넷이 막혀 있습니다. ChatGPT도 Copilot도 못 씁니다. 쓸 수 있는 건 사내 서버에 설치한 '작은 AI'뿐인데, 클라우드의 큰 모델보다 훨씬 덜 똑똑합니다."

### 5장 — 작은 AI에게 통째로 맡기면 사고가 납니다
- 사고 세 가지를 짧게: 멀쩡한 코드 삭제 / 없는 것을 지어냄(환각) / 절반만 고치고 끝.
- **하단 배너를 그대로 읽기**: "실수가 잦은 작은 AI로, 어떻게 중요한 코드를 안전하게 고칠 것인가 — 이게 저희가 풀어야 했던 문제입니다."
- 말로 덧붙일 포인트(사고의 뿌리): "기술적 뿌리는 처리량(토큰)입니다 — 작은 AI는 한 번에 다룰 수 있는 양이 좁은데, 파일 전체 재작성은 입력·출력을 최대로 만들어 앞뒤가 소리 없이 잘려 나갑니다. 그래서 다음 장처럼, 맡기는 처리량 자체를 줄였습니다."
- "실제로 있는 문제냐"는 질문이 나오면: "세 가지 모두 저희가 개발 중 실측으로 겪어 대응 장치를 만든 문제이고, 공개 연구로도 확인됩니다" → 문서 끝의 **[부록: 사고 3종의 근거 자료]** 인용.

### 6장 — 해결의 열쇠 ★ 가장 중요한 슬라이드
- 비유로: "실수가 잦은 신입에게 일을 통째로 맡기지 않고, 꼼꼼한 사수가 붙는 것과 같습니다."
- 왼쪽(프로그램=사수): 고칠 곳을 찾아 잘라 주고, 매뉴얼을 쥐여 주고, 결과물을 검수한다. "이건 같은 입력이면 늘 같은 결과가 나오는 일반 프로그램이라 틀리지 않습니다."
- 오른쪽(AI=신입): 잘라 준 조각 안의 코드만 쓴다.
- **하단 원리 문장을 강조**: "정확해야 하는 판단은 전부 프로그램이, 창작이 필요한 조각 하나만 AI가 — 발명 전체가 이 원리 하나입니다."

### 7장 — 실제 동작 다섯 단계
- 다섯 상자를 왼쪽부터: 요청 접수 → 파일 분해 → 위치 결정 → **조각 작성(주황색, AI 유일 관여)** → 검수·반영.
- "AI는 어디를 고칠지조차 모릅니다. 위치를 착각하는 실수 자체가 불가능하고, 실수해도 검수에서 걸러집니다."

### 8장 — 새로운 지점 다섯 가지 (A~E)
- "새롭다고 생각하는 지점이 다섯 개인데, A와 B가 중심이고 C·D·E는 보조 장치입니다."
- 다섯 줄을 빠르게 훑고 "이제 하나씩 조금만 더 자세히 보겠습니다."

### 9장 — Ⓐ 고칠 곳은 프로그램이 정한다
- 기존 방식(AI가 통째로 다시 씀, 결과가 AI 실력에 달림) vs 본 발명(프로그램이 위치 지정, AI는 조각만).
- 배너: "'작은 AI는 못 믿는다'는 문제를 AI 개선이 아니라 **처리 구조(방법)**로 해결한 점이 특허 관점의 핵심입니다."

### 10장 — Ⓑ 정답 매뉴얼을 자동으로 쥐여준다
- "코드에서 사내 함수 사용이 감지되면, 그 함수의 올바른 사용법 '정답지'를 AI에게 자동으로 첨부합니다. 지어낼 틈이 없습니다."
- 차이 강조: "흔한 방식(비슷한 문서를 확률로 골라 줌)과 달리, 조건이 맞으면 100% 첨부, 아니면 0%인 **확정 규칙**입니다."
- 배너: "'AI야 틀리지 마'라는 부탁(문구)이 아니라, 감지→첨부라는 **장치(기술 구성)**로 환각을 막았습니다."

### 11장 — Ⓒ·Ⓓ 두 겹의 안전장치
- C: "고칠 후보가 여럿이면 AI에게 객관식으로 묻고, AI는 '3번'처럼 번호만 답합니다."
- D: "AI가 준 코드를 컴파일러(문법·타입 검사기)로 검사하고, 문제가 있으면 한 번 자동 교정, 그래도 안 되면 원본을 지킵니다. 불합격품은 절대 반영되지 않습니다."

### 12장 — Ⓔ AI가 꺼져 있어도 동작한다
- "폐쇄망에서는 AI 서버가 꺼진 날도 일상입니다. 보통 도구는 먹통이 되지만, 저희는 미리 준비한 문서를 검색해 답합니다. 데이터는 어떤 것도 밖으로 나가지 않습니다."

### 13장 — 기존 도구와 나란히 비교
- 표의 둘째 줄이 핵심: "고칠 곳을 누가 정하는가 — 기존은 AI, 저희는 프로그램."
- **하단 배너 반드시 언급**: "부품 하나하나는 알려진 기술이라는 걸 저희도 압니다. 새로움은 이 조합의 구체적 방식에 있다고 생각합니다."

### 14장 — 비슷한 기술 예비 조사
- "발명자로서 아는 범위에서 찾아본 것이고, 정식 선행기술조사는 변리사님께 부탁드립니다." — 이 겸손한 프레임이 신뢰를 줍니다.

### 15장 + 16~23장 — 작동 도식 8장
- "지금까지 말씀드린 것이 실제 코드로 어떻게 도는지 도식 8장으로 준비했습니다. 실제 저장소의 파일·함수 위치에서 뽑아 그렸고, 청구항 쓰실 때 처리 흐름도 재료로 쓰실 수 있습니다."
- **전략**: 다 설명하지 말 것. 17장(01 전체 조감도)만 1분 설명하고 넘어가되, 변리사가 특정 도식에 질문하면 그때 멈춰서 설명.

### 24장 — 특허가 될 수 있을까: 아는 것과 모르는 것
- 왼쪽: "말뿐인 아이디어가 아니라 구체적 처리 단계이고, 실제로 돌아가는 제품이라 유리하다고 봅니다."
- 오른쪽: "하지만 신규성과 진보성은 저희가 판단할 수 없습니다. 그래서 오늘 왔습니다." — 자연스럽게 상담 요청으로 전환.

### 25장 — 출원 방향
- "중심 청구항은 Ⓐ+Ⓑ 결합 — 프로그램이 고칠 곳을 정하고, 정답 매뉴얼을 자동으로 쥐여주어, 작은 AI로도 안전한 편집을 보장하는 방법 — 으로 생각하고 있습니다. Ⓒ·Ⓓ·Ⓔ는 보조로 붙입니다."
- "이 구조가 타당한지가 오늘 가장 여쭤보고 싶은 것입니다."

### 26장 — 걱정거리 세 가지
- 감추지 않고 먼저: ①부품들은 공지 기술(조합으로 승부) ②공개 이력 점검 필요 ③개인/회사 어느 이름으로 낼지.

### 27장 — 질문 다섯 가지
- 하나씩 읽고 **답을 받아 적는 체크리스트**로 사용: ①선행기술조사 범위·기간·비용 ②공지예외 적용 가능성 ③청구항 구체화 수준 ④해외 출원 ⑤일정·서류.

### 28장 — 참고: 기본 정보
- 필요할 때 펼쳐 보는 참고 자료. ⚠ 두 항목(출원인, 공개 이력)은 26장과 연결됨.

### 29장 — 오늘 이후의 순서
- "오늘 방향이 확인되면 기술 요지서 → 선행기술조사 → 출원으로 가고 싶습니다. 모든 내용은 실제 코드와 도식으로 즉시 뒷받침됩니다. 감사합니다."

## 예상 질문과 답변 준비

**Q1. "소프트웨어 발명은 추상적 아이디어라고 거절되기 쉬운데요?"**
→ "그래서 '프롬프트를 잘 쓴다' 수준이 아니라, 위치 결정 → 매뉴얼 첨부 → 컴파일러 검사라는 구체적 처리 단계로 준비했습니다. 각 단계가 실제 코드와 도식으로 뒷받침됩니다." (7장, 도식으로 되돌아가기)

**Q2. "코드나 문서를 외부에 공개한 적 있습니까?"**
→ 솔직하게: "출원 전 전수 점검이 필요합니다"(26·28장). 미팅 전에 저장소 공개 여부·발표·배포 이력을 미리 정리해 갈 것. 공개가 있었다면 공지예외(12개월) 적용 가능성을 바로 질문.

**Q3. "직무발명 아닌가요? 출원인은 누구로?"**
→ "개발자 1인 발명이고, 회사의 직무발명 규정 확인이 필요합니다. 개인 출원과 법인 출원 중 어느 쪽이 맞는지 조언 부탁드립니다."

**Q4. "특허를 내면 방법이 공개되는데, 폐쇄망 제품이면 영업비밀로 지키는 게 낫지 않습니까?"** (변리사가 먼저 꺼낼 수 있음)
→ "그 트레이드오프를 알고 왔습니다. 전부가 아니라 공개해도 지킬 가치가 있는 중심(Ⓐ+Ⓑ)만 출원하고, 나머지 구현 디테일은 영업비밀로 남기는 이원화를 생각하고 있습니다. 그 경계선을 어디에 긋는 게 좋을지도 여쭙고 싶습니다."

**Q5. "Copilot·Cursor 쪽 특허와 충돌하지 않나요?"**
→ "저희 예비 조사로는 출발점(클라우드 큰 AI 전제)이 다르지만(13·14장), 특허문헌까지는 못 봤습니다. 그래서 정식 선행기술조사를 요청드리는 것입니다."

**Q6. "5장의 사고 세 가지 — 실제로 흔한 문제입니까? 근거가 있습니까?"**
→ "네, 세 가지 모두 ①저희가 실측 테스트(주 모델: qwen3-coder)에서 직접 겪어 대응 장치를 만든 문제이고, ②공개 연구·벤치마크로도 확인됩니다. 대표 수치 하나만 들면 — GPT-4o 같은 대형 모델조차 700줄 규모 코드를 통째로 다시 쓰게 하면 47%에서 코드를 생략합니다. 작은 모델은 더 심하고요. 기술적 뿌리는 처리량(토큰) 한계입니다 — 통째 재작성은 입력·출력을 최대로 만들어 앞뒤가 잘려 나가고, 그 증상이 사고 3종으로 나타납니다. 그래서 '통째로 맡기지 않는 구조'가 필요했던 것입니다." ## 부록 — 사고 3종의 근거 자료 (5장 뒷받침)

발명의 배경(해결 과제)이 실재함을 보이는 자료. 변리사가 근거를 물으면 이 부분을 인용한다.

### 사고 1. 멀쩡한 코드를 지워 버립니다 — "laziness(생략)" 문제
- **공개 연구**: 대형 모델(GPT-4o)조차 코드를 통째로 재작성시키면 **200줄 이하에서는 1.67%, 700줄 규모에서는 47.4%가 코드를 생략·누락**. 해법으로 "작은 단위로 쪼개 맡기기"를 제시 — 본 발명의 접근과 동일. → [LLMigrate (arXiv 2503.23791)](https://arxiv.org/html/2503.23791v1)
- **공개 연구**: LLM이 "작업과 무관한 코드를 삭제해 기존 기능을 파괴"하는 실패 유형 보고. → [Can LLMs be Effective Code Contributors? (arXiv 2604.23340)](https://arxiv.org/pdf/2604.23340)
- **자체 실측**: 파일 전체 재작성 경로에서 태그·라인 수가 급감하는 파손을 겪고 "파괴적 누락 거부 가드"를 구현. 부분 편집에서 닫는 태그가 조용히 사라지는 사고도 별도 가드로 차단.

### 사고 2. 없는 것을 지어냅니다 — 환각(hallucination)
- **공개 연구**: 코드 생성 환각 중 **API 지식 충돌(없는 함수·틀린 사용법)이 20.4%**. 모델 크기가 작을수록 환각 빈도 증가(DeepSeek-Coder 1.3B → 7B → 671B로 갈수록 감소). → [LLM Hallucinations in Practical Code Generation (arXiv 2409.20550)](https://arxiv.org/html/2409.20550v1)
- **공개 분석**: "작은 모델이 유의하게 더 환각한다(p=0.01)". → [Do Smaller Models Hallucinate More? (Vectara)](https://www.vectara.com/blog/do-smaller-models-hallucinate-more)
- **자체 실측**: import 경로를 존재하지 않는 모듈로 지어냄, 사내 표준 조회 함수의 응답 규약을 몰라 임의 코드로 회귀, API 주소 바꿔치기 등 — 각각 결정론 교정 장치(Ⓑ 계약 주입 등)로 해결. 사내 전용 API는 학습 데이터에 없어 **구조적으로 지어낼 수밖에 없는 영역**이라는 점이 Ⓑ의 존재 이유.

### 사고 3. 절반만 고치고 끝냅니다 — 불완전 편집
- **자체 실측(가장 직접적)**: "달력 입력으로 바꿔줘" 요청에 qwen3-coder가 **import 한 줄만 추가하고 멈춘** 사례 — 골격 슬롯 주입(Ⓑ 레시피 카드)으로 해결. 실측 실패 유형으로 "블록 누락 — 모델이 설명만 쓰고 종료"가 개발 문서에 기록됨([multi-task-decomposition.md](multi-task-decomposition.md)).
- **공개 보고 (qwen3-coder 특정)**: 편집 도구 호출 실패 · Search/Replace 블록 미출력으로 파일 통째 재작성으로 회귀하는 문제. → [opencode #6918](https://github.com/anomalyco/opencode/issues/6918), [void #857](https://github.com/voideditor/void/issues/857)
- **공개 문서**: "약한 모델은 코드 편집 형식을 제대로 반환하지 못한다" — Aider 공식 문서. → [Aider support docs](https://github.com/QwenLM/Qwen3-Coder/blob/main/qwencoder-eval/instruct/aider/aider/website/docs/troubleshooting/support.md)

### 사고 3종의 공통 뿌리 — 처리량(토큰/컨텍스트) 한계
- **자체 실측**: ①컨텍스트 창 설정이 실제 서버에 전달되지 않아 기본 4096 토큰으로 돌면서 **긴 프롬프트의 앞부분(지시·규약)이 소리 없이 잘려** 응답이 망가진 사고(이후 서버 모델을 64k로 재빌드, [vastai_ollama_litellm_setup.md](vastai_ollama_litellm_setup.md)) ②대화 히스토리 누적이 창을 잠식해 **빈 응답/잘림**을 만들던 문제([multi-task-decomposition.md](multi-task-decomposition.md) 불변식 1·2) ③추론(thinking) 토큰이 응답 토큰을 다 써버려 **빈 응답**이 되던 문제([AI_SERVER_SETUP.md](AI_SERVER_SETUP.md)).
- **공개 연구와의 일치**: LLMigrate의 생략률이 코드 길이에 비례(200줄 1.67% → 700줄 47.4%)한다는 것 자체가 "처리량이 커질수록 실패"의 정량 증거.
- **발명과의 연결**: 본 발명의 조각 편집은 이 뿌리의 직접 해법 — 개발 계기판(`eval:region`)의 핵심 지표가 **토큰 절감**이며, 명세서에서 "토큰 사용량 절감"을 **측정 가능한 정량적 효과**로 기재할 수 있는 재료.

### 말할 때의 뉘앙스 (정직한 프레임)
- qwen3-coder는 소형 코더 중 상위권 — "작은 AI는 무조건 멍청하다"가 아니라 **"파일을 통째로 재작성시키는 방식이 작은 모델에서 특히 위험하다"**(코드가 길수록 · 사내 전용 규약일수록 · 컨텍스트가 길수록)가 정확한 주장.
- GPT-4o의 47% 생략률은 역으로 활용 가능: "큰 모델도 통째 재작성은 위험 → 모델 개선이 아니라 **구조(방법)로 푸는 본 발명**의 가치".

## 발표 팁

- **절대 버리면 안 되는 슬라이드**: 5장(문제) → 6장(해결 원리) → 9·10장(Ⓐ·Ⓑ) → 25장(출원 방향) → 27장(질문). 시간이 없으면 이 여섯 장만으로도 미팅이 성립합니다.
- **시간이 부족할 때 버리는 순서**: 도식 상세(18~23) → 12장(Ⓔ) → 11장(Ⓒ·Ⓓ) → 14장(예비 조사).
- 6장의 원리 문장("정확해야 하는 판단은 전부 프로그램이, 창작이 필요한 조각 하나만 AI가")은 미팅 중 최소 세 번 반복 — 6장, 13장 비교 후, 25장 출원 방향에서.
- 미팅의 성공 기준 = **27장 질문 5개에 답을 받고, 25장 중심 청구항(Ⓐ+Ⓑ) 방향에 대한 피드백을 받는 것.**
